# LINE สำหรับ Locomall: แนวทางและขอบเขต

ตรวจเอกสารวันที่ 12 ตุลาคม 2026

## สิ่งที่ทำในรอบนี้

เพิ่มการระงับ/คืนสิทธิ์ร้านโดย Platform Admin ในหน้า Admin → ภาพรวม → ดูแลร้านค้า
ระบุเหตุผล 1–500 ตัวอักษรและยืนยันก่อนทำรายการ; ค้นหาชื่อร้าน กรองสถานะ ดึงลงรีเฟรช
และอัปเดตผ่าน Realtime ได้ ใช้ migration `20261012040048_admin_store_suspension.sql`.

- ตรวจสิทธิ์จาก `platform_roles` ฝั่งฐานข้อมูล ไม่ใช้ชื่อผู้ใช้หรือ UI เป็นการยืนยันสิทธิ์
- public RPC เป็น SECURITY INVOKER เรียกฟังก์ชัน private ที่ตรวจตัวตน/สิทธิ์อีกครั้ง
  ไม่มีการเปิดสิทธิ์ UPDATE ตารางร้านให้ client
- ระงับได้เฉพาะร้านที่อนุมัติแล้ว คืนสิทธิ์ได้เฉพาะร้านที่ระงับและตลาดยังอนุมัติอยู่
- ป้องกันคำสั่งจากข้อมูลเก่าด้วย `updated_at`; กดซ้ำสถานะเดิมไม่สร้างประวัติ/แจ้งเตือนซ้ำ
- Lock แถวร้านร่วมกับ checkout เดิม ทำให้ COD/Wallet เงินจำลองไม่ข้ามการระงับ
  หาก checkout ได้ lock ก่อน ออเดอร์นั้นเสร็จก่อนการระงับและถือเป็นออเดอร์เดิม
- Catalog รายละเอียดร้านและการใส่ตะกร้าเดิมตรวจ approved; ออเดอร์ใหม่ถูกปฏิเสธ
  แม้ผู้ซื้อยังมีสินค้านั้นในตะกร้า การเอาออกจากตะกร้ายังทำได้
- ไม่ลบออเดอร์เดิม ไม่ปรับ stock/reservation/ledger ไม่คืนเงินหรือยกเลิกอัตโนมัติ
  ผู้ขายยังต้องจัดการงานค้าง การยกเลิก/คืนเงินใช้ flow เดิม
- ห้ามสร้าง seller listing ใหม่ขณะที่ร้านถูกระงับ แม้มีคำขอผู้ขายร่วมที่รอตรวจ
- แจ้งผู้ดูแลร้าน ผู้ขายร่วม และเจ้าของตลาดแบบ distinct โดยไม่แจ้งคนที่ทำรายการเอง
  ไม่แจ้งลูกค้าหรือผู้ติดตามที่ไม่ใช่ผู้เกี่ยวข้องในฐานะผู้ดูแล/ผู้ขาย
- บันทึก actor, สถานะเดิม/ใหม่ และเหตุผลในประวัติ ห้ามใส่ข้อมูลส่วนบุคคลอ่อนไหวในเหตุผล
- คืนสิทธิ์ร้านไม่ทำให้ผู้ขายที่พักขายกลับมา active และไม่ส่งข่าวร้านใหม่ให้ followers

ไม่ใช่การแบนบัญชี การปิดตลาด โหมดปิดระบบ หรือ blacklist ถาวร และยังไม่มี LINE webhook/token/การส่งจริง
ระบบเหล่านี้ต้องกำหนดผลต่อออเดอร์ค้าง การอุทธรณ์ และการเข้าร่วมตลาดใหม่แยกต่างหาก.

## 1. ช่องทาง Admin กับเจ้าของตลาด

### หากโจทย์ระบุ OpenChat จริง ๆ

ใช้ OpenChat เป็นพื้นที่ประกาศที่ผู้ดูแลโพสต์เองก่อน ไม่ออกแบบให้ Messaging API ส่งตรงเข้า OpenChat
เอกสาร [Messaging API สำหรับกลุ่ม](https://developers.line.biz/en/docs/messaging-api/group-chats/)
รองรับ LINE group chat/multi-person chat ซึ่งเป็นคนละประเภทกับ OpenChat;
[LIFF](https://developers.line.biz/en/docs/liff/developing-liff-apps/) ยังระบุว่า share target picker ไม่รวม OpenChat
จึงไม่ใช้ LIFF เป็นทางลัดเพื่อส่งเข้าห้องนี้อัตโนมัติ.

ขั้นตอนเริ่มต้น:

1. สร้างห้องสำหรับ Admin และเจ้าของตลาด ตั้งให้ต้องขออนุมัติเข้าร่วม ไม่ใช้ห้องเปิดให้ใครก็เข้าได้
2. ตรวจผู้ขอเข้าห้องกับบัญชี Locomall และตลาดที่อนุมัติแล้วนอกห้องก่อนรับเข้า
   ไม่ขอรหัสผ่าน/โทเคนหรือข้อมูลส่วนบุคคลในห้อง และไม่เชื่อแค่ชื่อที่ตั้งใน LINE
3. ให้ชื่อในห้องมีรหัสตลาดเพื่อช่วยตรวจสอบ แต่ยังต้องตรวจตัวตนจริง
   [คู่มือ OpenChat](https://openchat.line.me/th/guide) อธิบายว่าโปรไฟล์ห้องแยกจากบัญชี LINE หลัก
4. Admin ตรวจประวัติในแอปแล้วโพสต์ เช่น “ร้าน #12 ถูกระงับรับออเดอร์ใหม่ ตั้งแต่ …”
   เรื่องส่วนตัวและรายละเอียดเหตุผลส่งเฉพาะผู้เกี่ยวข้อง ไม่โพสต์ข้อมูลผู้ซื้อ/ที่อยู่/ยอดเงินในกลุ่ม
5. ตรวจสมาชิกเป็นระยะและนำผู้ที่หมดสิทธิ์เจ้าของตลาดออกด้วยตนเอง
   การระงับในฐานข้อมูลไม่ได้ลบสมาชิก OpenChat อัตโนมัติ

อาจเพิ่มปุ่มคัดลอก “ข้อความประกาศที่ปลอดภัย” ฝั่ง Admin ในงานรอบถัดไปได้
แต่รอบนี้ยังไม่ได้ทำปุ่มหรือใช้ native Share ที่พักไว้ก่อน.

### หากต้องการส่งสถานะอัตโนมัติ

แนะนำ **กลุ่ม LINE ปกติแบบส่วนตัว + LINE OA bot** แทน OpenChat ตาม
[เอกสาร LINE](https://developers.line.biz/en/docs/messaging-api/group-chats/):
เปิด Allow bot to join group chats แล้วเชิญ OA เข้ากลุ่ม กลุ่มหนึ่งมี OA ได้หนึ่งบัญชี
รับ `groupId` จาก webhook ที่ตรวจ signature แล้ว; ไม่ให้ client ใส่ปลายทางส่งเอง.

การทำงานที่เสนอ (ยังไม่ติดตั้ง):

1. Admin ทำรายการในแอป การเปลี่ยนสถานะจริงและบันทึก event ลง outbox สำเร็จใน transaction เดียวกัน
2. Edge Function/worker อ่าน event ส่งประกาศไปยัง groupId ที่กำหนดไว้ฝั่ง backend
3. เก็บ event ID, สถานะส่ง, จำนวนครั้งและเวลาที่ลองอีกครั้ง ป้องกันส่งซ้ำและรองรับ retry
4. LINE ล่ม/โควตาหมดต้องไม่ย้อนกลับการระงับหรือขัดขวาง checkout; กลับมาลองส่งภายหลัง
5. การอนุมัติ/ระงับ/คืนสิทธิ์และประกาศบำรุงรักษาใช้ข้อความแยกประเภท
   ไม่มีการส่งทุกครั้งที่ stock หรือออเดอร์ของลูกค้าเปลี่ยนไปยังกลุ่มนี้
6. กลุ่มส่วนตัวยังต้องดูแลการเชิญสมาชิก ไม่ใช่การ enforce role แบบ RLS อัตโนมัติ
   ถ้าต้องการตรวจบัญชี LINE กับบทบาท ต้องทำ account linking และตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์
7. ประกาศปิดระบบต้องมีสถานะ maintenance ของจริงใน backend ก่อน ไม่ใช่แค่ส่งข้อความ
   หาก backend เองล่มต้องมีผู้ดูแลประกาศด้วยตนเองได้

ต้องเตรียม OA, Messaging API channel, Channel secret, Channel access token และกลุ่มทดสอบ
เก็บ secret/token ใน Supabase Secrets เท่านั้น ห้าม `EXPO_PUBLIC_*`, APK หรือ Git
รับ webhook ผ่าน HTTPS และ [ตรวจ signature จาก raw request body](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/)
ก่อนเชื่อ userId/groupId/event ที่ได้รับ ต้องกรองกลุ่มปลายทางที่อนุญาตไว้ก่อน.

## 2. LINE OA ระหว่างแอปกับผู้ใช้

แนะนำเริ่มแบบจำกัดขอบเขต: **ช่องทางติดต่อทีมดูแล + FAQ + เมนูช่วยเหลือ**
ยังไม่แทนแชตผู้ซื้อ–ร้านค้า และไม่ส่งแจ้งเตือนทุกอย่างซ้ำกับ push.
[Messaging API overview](https://developers.line.biz/en/docs/messaging-api/overview/) รองรับ rich menu,
ข้อความตอบกลับ และการเชื่อมบัญชีบริการกับบัญชี LINE.

ประโยชน์: ผู้ใช้มีช่องทางแจ้งปัญหาแม้เข้าแอปไม่ได้, แยกงาน support จากบทสนทนากับร้าน
และใช้สาธิตการทำงานร่วมกับ LINE ได้โดยไม่ต้องทำระบบซื้อขายใน LINE ใหม่.

ผลกระทบที่ต้องเตรียม:

- ต้องมีผู้ดูแลตอบและกำหนดเวลาติดต่อ ไม่เช่นนั้นผู้ใช้เข้าใจว่ามีช่องทางช่วยเหลือแต่ไม่ได้รับคำตอบ
- ถ้าจะดูออเดอร์เฉพาะคนหรือส่งสถานะส่วนตัว ต้อง [เชื่อมบัญชีอย่างปลอดภัย](https://developers.line.biz/en/docs/messaging-api/linking-accounts/)
  หลังล็อกอิน Locomall พร้อมความยินยอม และ nonce/link token ใช้ครั้งเดียว
  ห้ามยืนยันจาก LINE display name, email ที่ผู้ใช้พิมพ์เอง หรือ userId ที่ client ส่งมาเฉย ๆ
- OA userId ไม่ใช่ Supabase userId ต้องมี mapping ที่ client อ่าน/แก้ของคนอื่นไม่ได้
  ต้องมีการยกเลิกการเชื่อม/ปิดการแจ้งเตือนส่วนตัวได้
- ข้อความออเดอร์ควรแสดงข้อมูลน้อยที่สุดและลิงก์เข้าแอป ตรวจ ownership อีกครั้งก่อนเปิดรายละเอียด
  ไม่มีคำสั่งคืนเงิน/ยืนยันรับสินค้า/เปลี่ยนสถานะโดยอ่านข้อความที่ไม่ได้ตรวจตัวตน
- ผู้ใช้อาจบล็อก OA หรือการส่งอาจไม่สำเร็จ จึงยังเก็บข้อมูลจริงและแจ้งเตือนในแอป
- Push/broadcast มีโควตาและอาจมีค่าใช้จ่ายตามแพ็กเกจ กลุ่มนับตามจำนวนผู้รับ
  Reply ผ่าน Messaging API ไม่ถูกนับแบบเดียวกับ push ต้องติดตาม quota/consumption และจำกัดการส่ง
  ดู [ราคาและวิธีนับข้อความของ LINE](https://developers.line.biz/en/docs/messaging-api/pricing/)
- กำหนดข้อมูลที่จะส่งให้ LINE และอธิบายให้ผู้ใช้ทราบ ไม่ส่งข้อมูลทั้งหมดโดยอัตโนมัติ

## ข้อเสนอการแบ่งเฟส

1. ตอนนี้: ใช้ระงับร้านในแอป + สรุปบทบาท/นโยบาย; เลือกกับอาจารย์ว่า OpenChat โพสต์ด้วยคน
   หรือกลุ่ม LINE ปกติส่งอัตโนมัติ ตัดสินใจก่อนตั้ง backend ส่งข้อความ
2. Prototype ถัดไป: OA สำหรับ support และ rich menu; หากเลือกกลุ่มปกติ เพิ่ม outbox/worker
   เฉพาะอนุมัติตลาด/ระงับร้าน/คืนสิทธิ์ ไม่เพิ่มคำสั่งแอดมินใน LINE
3. ต่อมาเมื่อจำเป็น: เชื่อมบัญชีผู้ใช้และ opt-in แจ้งสถานะสำคัญส่วนตัว ไม่คัดลอกแชตทั้งหมดไป LINE

ยังไม่สร้าง OA/OpenChat จริง ยังไม่ผูกบัญชี และยังไม่ส่งข้อความใดใน LINE จากโปรเจ็กต์นี้.

## การทดสอบและข้อจำกัด

ทดสอบ migration ใน PostgreSQL จำลองด้วย PGlite: Admin/Buyer/Market owner/Store manager/co-seller,
การเขียนตรง, คำสั่งซ้ำ, เวอร์ชันเก่า, เหตุผลว่าง/ยาวเกิน, คืนสิทธิ์ในตลาดปิด,
COD/Wallet ถูกปฏิเสธโดยไม่หักยอด/จองสต็อก, รับงานออเดอร์เดิม, คืนสิทธิ์โดยคง paused listings
และการแจ้งเตือนผู้เกี่ยวข้องที่ไม่ซ้ำกับ followers.
ใช้ COD RPC จริงสำหรับ delivery ใน fixture; PostGIS แทนด้วย domain เพราะไม่ทดสอบระยะทางรอบนี้
ไม่ได้ทดสอบการแข่งขันระหว่าง connection จริงหรือการส่ง push บนอุปกรณ์จากกรณีนี้
ก่อนออก APK ต้องทดสอบร้านเปิดขาย → ระงับ → checkout ถูกปฏิเสธ → จัดการออเดอร์เดิม → คืนสิทธิ์
ด้วยหลายบัญชีบนเครื่องจริงเพิ่มเติม.

ติดตั้ง migration บน Supabase แล้ว ตรวจ Admin/บัญชีทั่วไป/anon, ระงับ–คืนสิทธิ์,
การกดซ้ำ/เวอร์ชันเก่า, catalog ที่ซ่อนร้าน และคงสต็อก/ออเดอร์/ledger บนฐานข้อมูลจริง
ใน transaction ที่ `ROLLBACK` ทั้งหมด ไม่ทิ้งข้อมูลระงับหรือการแจ้งเตือนจากการทดสอบไว้
Security Advisors ก่อน/หลังไม่มี finding ใหม่จากงานนี้ คำเตือนเดิมเรื่อง
[RPC SECURITY DEFINER](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)
และ [Leaked Password Protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)
ยังอยู่ ไม่ได้อ้างว่าการตรวจรอบนี้เป็นการแก้คำเตือนเดิมทั้งหมด.
